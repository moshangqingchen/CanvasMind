# 提交、失败、扣费、取消与恢复复核 · 2026-10-05

本轮针对最近修改的这条业务流程复核，检查接口、供应商响应处理、运行时持久化与界面展示。没有继续扩展功能或改动 UI 布局。测试使用隔离数据和模拟供应商。

## 已复现的问题与来源

| 问题 | 来源核对 | 最终行为 |
| --- | --- | --- |
| 同一退款的摘要为 `refunded: true`，退款明细却是 pending、processing 或明确否定，仍显示已退款 | 当前新增的扣费解析代码遗漏 | 不确认退款；有原扣费凭据时保留原扣费，否则显示待确认 |
| 同一收据的币种别名互相矛盾，仍选择第一个并显示金额 | 当前新增的扣费解析代码遗漏 | 保留明确的扣费或退款状态，省略冲突的金额与币种；原扣费与退款各自使用不同币种仍受支持 |
| 已收到供应商响应，进度回调报连接准备错误，提示却称尚未提交并建议重试 | HEAD 原有文案也可复现；上轮只修正了结构化发送状态 | 提示核对原任务与账单，避免重复提交；查询阶段仅恢复原任务操作 |
| 用户取消时，原任务的查询结果随后返回，终态与账务凭据漏存 | 视频场景在 HEAD 原代码同样复现；本轮同时覆盖图片路径 | 保持本地取消状态，只补记同一任务的凭据，不重新提交、继续轮询或自动归档 |

业务代码只改动 `packages/providers/src/charge-evidence.ts`、`packages/providers/src/error-presentation.ts`、`packages/runtime/src/service.ts`。本轮开始时的文件哈希与收尾结果核对，其余九个受检业务文件没有变化。

取消回执合并以最新落库记录为准，校验原任务编号，并通过串行处理与条件更新避免旧取消操作覆盖较新退款或终态。交叉审查同时拦截并修正了该补丁中的停机后写入、旧错误文字覆盖新取消结果，以及空值类型问题。更新诊断时，旧诊断未变化才采用本次结果；期间新添的诊断完整保留，费用单独合并。

## 本轮验证

新增 12 个回归用例：Providers 3 项、Runtime 9 项。核心失败场景先在修复前复现，再验证修复后的行为。运行时额外检查了旧取消操作与新退款竞争、取消成功清除旧失败提示、CLI 停止跟踪文案、停机与另一实例取消、错误任务编号，以及较新终态和退款保持。

最终单元与接口检查共 **1,184 项通过**：

- Providers：44 个文件，789 项，全包。
- Runtime：17 个文件，282 项，全包。
- Renderer/API：13 个文件，113 项，覆盖运行接口、公开错误字段、失败诊断、来源详情数据、原任务恢复和结果同步。
- 工作区 `pnpm typecheck` 通过，其中重新构建共享包并检查各工作区类型。
- Next 生产构建通过；使用重新构建的版本进行浏览器验证。

浏览器 **7 个文件、22 个场景一次运行全部通过**，没有失败重试，覆盖：

- 提交响应丢失后关闭并重开页面，找回原任务，生成 POST 始终只有一次。
- 查询失败、响应暂缺任务及超过 50 个任务时继续跟踪原任务。
- 余额不足、供应商缺号、本机连接失败、链路异常，以及已扣费、未扣费、金额缺币种等展示。
- 结果卡片、来源详情和运行历史中的费用一致，刷新后仍保留，后续新到账务信息正常保存。
- 最新成功状态清除旧失败诊断；取消状态展示真实费用及“取消不等于退款”。
- 取消后只取回已有图片，不恢复生成或再次提交；错误卡片拖动、滚动和控件仍可用。

查看了本轮浏览器截图中的窄窗口扣费详情和取消费用详情；文字、金额和关闭按钮可读可用，没有横向溢出。构建与浏览器检查结束后再次比较冻结文件哈希，业务源文件没有在验证过程中变化。

浏览器使用 renderer 目录下 `pnpm exec playwright test`，限定 `generation-failure-details`、`task-evidence`、`result-information`、`run-output-recovery`、`canvas-result-errors`、`canvas-run-reconciliation` 和 `canvas-polish` 中相关场景，输出目录为 `test-results-final-acceptance`。

主要日志位于 `.codex-temp/final-acceptance-*.log`。上轮全量检查见 [FAILURE-RECHECK.md](FAILURE-RECHECK.md)，其测试数量不并入本轮结果。

## 验证边界

本轮没有调用真实付费生成接口，没有产生真实供应商扣费，也没有打包、安装或发布桌面版本。供应商真实返回的账务信息只有在响应明确提供时才能确认；缺失或冲突的凭据仍显示待确认，不能据测试结果推断实际账户是否扣款。
